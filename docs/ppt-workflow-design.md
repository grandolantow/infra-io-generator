# AI PPT 工作流：Codex 实现说明

版本：设计基线 v0.1
定位：描述待实现的工作流、边界与验收标准，不表示生成/导出工具已经实现或通过测试。

## 1. 目标与核心决定

实现一个轻量、可定制、支持中间预览的 PPT 工作流。

用户交互：资料与意图 → 大纲确认 → 布局预览确认 → HTML 迭代确认 → PPTX 交付。

技术架构：轻量主 skill + 可组合场景配方 + 可选布局探索 + 同源 HTML/PPTX 生成。

优先解决：主线清楚、信息密度适当、布局可探索、局部修改不漂移、最终文件可检查。

可以从头设计。旧 skill 与公开仓库只作参考，不要求兼容旧目录、旧文件格式或旧约束。不要将旧的“HTML 为唯一最终交付、禁止 PPTX”规则继承到新流程。

## 2. 主 skill 的职责

主 skill 负责识别任务、选择配方、推进阶段、尊重确认结果、调用生成与检查工具。保持简短，场景细节与技术说明按需读取。

通用原则：

- 有依据的事实、计算推导与工程判断分别表达；不得补造数字或把未验证内容写成实测结论。
- 默认在大纲、布局、HTML 三处确认；用户可指定跳过、合并或停在某阶段。
- 已知信息不重复询问，只追问会实质改变主线或交付方式的缺口。
- 用户指定修改页或模块时，保留其他已确认内容和设计。全局变更需要明确授权。
- 保留可修改源；HTML/PPTX 生成后进行实际检查，未完成的检查如实说明。
- 提供可访问的文件或下载链接，不只返回裸路径；不能把整页图片包装成原生可编辑 PPT。

不要写入全局硬规则：固定五问、固定三条结论、固定页数、每页必须趋势分析、每页必须昇腾影响、统一高密度、统一字号、必须讲稿、必须使用某个绘图工具。

## 3. 场景与视觉独立配置

四种场景是叙事配方，不是四套重复的 skill，也不是必须填满的栏目表。

| 场景 | 默认组织方式 | 非必选内容 |
| --- | --- | --- |
| 论文分享 | 问题与已有方法 → 核心想法 → 机制 → 实验与局限 → 可借鉴点 | 趋势预测、昇腾适配、商业判断 |
| 技术点分享 | 具体问题 → 直观模型 → 数据流/执行流 → 实现细节 → 示例与边界 | 宏观综述、完整论文结构 |
| 洞察报告 | 变化与判断 → 证据与机制 → 成本/瓶颈 → 影响与取舍 → 行动建议 | 无证据的趋势预测、强行下结论 |
| 组内分享 | 现象或问题 → 关键解释 → 案例/演示 → 踩坑与讨论 | 正式汇报口吻、强行拔高 |

允许组合，例如“论文分享的结构 + 组内分享的语气”。场景、语气、密度、视觉风格、交付格式分开处理，由自然语言推导；不要求用户填写配置表。

“昇腾模型洞察”放在洞察场景下面作为可选特化：模型变化 → 设计动机 → 计算/存储/通信变化 → 框架与芯片影响 → 待验证判断。

“微软雅黑、18/12/10 磅、红色标题、高信息密度”保存为可选技术洞察预设，不覆盖其他场景。用户参考图和本次明确要求优先于默认预设。

## 4. 默认执行流程与中间产物

### A. 资料与大纲

先整理每页的：问题或主旨、关键内容、证据/待补项、建议图示、与前后页的关系。

提供易讨论的大纲，不必提前写完整讲稿和大型报告。默认等待大纲确认再做视觉制作。非关键资料缺口允许标注后推进。

### B. 布局探索

可采用“生成整页视觉草图”的思路，借鉴 baoyu-slide-deck 的布局探索方式，不继承整页图片作为最终 PPT 的输出路线。

输入：已确认大纲、代表性真实内容、参考图、场景与视觉要求。

输出：布局预览图 + 简短布局记录（阅读顺序、区域划分、比例、主视觉、密度与需要保留的设计）。

优先选择最复杂、最有代表性的正文页，不只做封面。已有明确参考时出一个方案；存在实质构图取舍时可出两个。简单页面或已确认主题可以跳过探索。

有图像生成能力时，可生成布局图片；没有时，用简要线框排版并截图。工具可替换，不绑定某一图像模型或平台。

图片用于确定构图、视觉层级、图文比例与密度方向。不能把生成图片中的数字、公式、结构关系当作事实来源，也不能认为草图已经证明真实文本一定放得下。

选定后记录布局意图，HTML 阶段从原始内容重建文本、表格和图形，不通过 OCR 或逐像素复刻生成图片来恢复技术内容。发现实际内容容纳不下时，说明冲突并调整局部布局。

最终技术页面默认使用真实文本、可修改框图/图表和有出处的论文原图。布局草图不直接铺满最终 PPT 页面。

### C. HTML 制作与迭代

以正式内容和选定布局实现一张代表页，再扩展至全稿。默认单文件离线 HTML，固定幻灯片画布、等比缩放，不做无固定页高的长滚动网页；源文件可按页拆分。

用户通过自然语言、截图或页码批注修改。AI 修改对应页面源后重新生成 HTML，不同时维护另一套独立 PPT 文案。

每轮主要呈现更新 HTML、受影响页预览和简短改动说明。细节调整不反复重新审批整份大纲。

对于新的复杂视觉方案，HTML 制作阶段内部做一次代表页 PPTX 试导出，以提前发现导出边界。无需增加用户确认节点。

### D. PPTX 输出与验收

HTML 确认后，从同一版本页面源生成完整 PPTX，重新渲染最终文件检查。HTML 预览通过不等于 PPTX 验收通过。

交付 PPTX、HTML 和必要源文件；讲稿/补充材料按需提供。

三个默认确认点：大纲、布局、HTML。PPTX 导出后的技术检查由工具和 AI 执行；只有发现影响已确认内容/设计的冲突时才回到用户确认。

## 5. 同源输出架构

不要实现成“做完任意 HTML → 再让模型重新制作一份 PPT”。不建设任意 HTML/CSS 到 Office 的通用转换器。

推荐一份轻量页面源驱动两个输出端：

    当前页面源 + 共享视觉配置 + 素材
                    ├── HTML 预览
                    └── PPTX 输出

页面源至少承载当前正文、布局、图元、样式、备注与必要来源。页面和关键模块有稳定 ID，支持定向修改。

可以采用单页 JSON、YAML 或等价结构；具体格式由实现选择，不为了通用性设计庞大的 DSL。初期优先覆盖文本、框形、连线、表格和图片等常见对象，其他能力按用例扩展。

叙事规划阶段，大纲是内容讨论入口；进入制作阶段后，页面源是当前稿件的权威版本。大纲保留叙事意图，不另外维护一套需要手工同步的完整正文。主线改变时同步更新大纲。

“调整 HTML”的实际含义：用户在 HTML 上反馈 → AI 修改页面源/共享样式/对应布局实现 → 重新生成 HTML；最终 PPTX 来自同一版本。

不支持的对象必须明确处理：新增双端实现，或提示并采用局部图像回退，或调整设计。不得静默丢失内容或将整页截图后称其为可编辑。

坐标、字号与物理页面尺寸应使用明确一致的映射。正文密度通过结构调整处理，不以静默缩小字号或裁切作为默认兜底。字体缺失要记录替代情况，并验证换行和边界；不得打包分享字体文件。

## 6. 稳定性与多样性

稳定项：事实与口径、术语、页面/模块 ID、同份稿件的视觉语言、已确认布局、局部修改边界、输出版本。

可变项：叙事顺序、主视觉形式、左右比例、图文比例、密度、流程/对比/架构/表格/案例等构图。

原则：确认前允许探索；确认后减少自由重设计。新增页面继承同一设计语言，不要求与已有页使用同一模板。

变更作用域至少能区分内容、布局和全局主题。例如“第二页右侧改成流程图，其他不动”只影响该模块。

允许自定义构图，但新增组件需要同步考虑 HTML 和 PPTX 表达能力。受限输出支持不应被误解为只能使用少数固定模板。

## 7. 可编辑性与导出边界

| 对象 | 第一版目标 |
| --- | --- |
| 标题、正文 | 原生可编辑文本 |
| 普通配置表 | 原生可编辑表格 |
| 普通框图与箭头 | 原生形状、文本与连线 |
| 论文原图与截图 | 图片，保留出处 |
| 复杂公式、特殊图形 | 保留可修改源，说明最终编辑粒度；允许必要的局部矢量/图像回退 |
| 数据图表 | 优先使用可编辑图表；复杂类型按能力说明 |

SVG 清晰可缩放，不等于原生图元可逐项编辑。可编辑范围按实际对象说明，不笼统承诺全量可编辑。

初版不承诺 PowerPoint 手改后自动回写源文件。用户已手改 PPTX 时，继续生成前识别变更或确认处理方式，不能盲目覆盖。

## 8. 实现规模与交付建议

建议结构：

    ppt-workflow/
    ├── SKILL.md
    ├── references/
    │   ├── scenarios.md
    │   ├── visual-presets.md
    │   └── rendering.md
    └── scripts/

这不是强制目录契约，可采用更简单的等价实现。布局探索是一个可选能力，不必成为独立 skill 或独立 agent。视觉预设是配置，不是另一套工作流。

第一版优先复用成熟的渲染/导出库，不自行重写 Office 文件格式。开始实现前检查运行环境和依赖能力，不能将 README 的能力描述直接当成已测试结论。

不先做：大型模板库、模板市场、完整浏览器拖拽编辑器、固定多 agent 团队、复杂自动评审系统、任意 HTML 通用转换、PPTX 双向同步。

保留本地可检查的版本和修改记录即可，不要求自动提交或推送远程仓库。

## 9. 最小验收用例

先用 K3 的复杂技术正文页跑通完整流程，再用组内分享页验证可变性，不急着批量制作整套材料。

必须验证：

1. 场景可以切换和组合，不把趋势/昇腾/高密度要求强加给 casual 分享。
2. 大纲、布局、HTML 三个阶段有真实可查看产物，并支持按用户要求跳过。
3. 布局图片进入结构化页面制作，不作为最终整页底图。
4. HTML 固定页尺寸，无意外滚动扩高、缺图、文本溢出或模块遮挡。
5. 修改指定页/模块，不改变其他页的内容和已确认样式。
6. HTML 与 PPTX 来自同一稿件版本，关键文字、数据、页数与来源一致。
7. 最终 PPTX 被实际渲染检查；普通文本、表格和框图可编辑，特殊对象的回退明确。
8. 交付文件可以实际访问。未完成测试或依赖限制单独说明，不写成“全部通过”。

Codex 完成首轮后，应报告：已实现能力、用例与实际检查结果、已知边界、如何启动一次新任务和如何修改现有页面。

## 10. 总结

图片负责探索，HTML 负责反馈与迭代，PPTX 负责交付。

主 skill 保持轻量；场景和视觉可组合；页面源统一；确认后局部修改；最终文件单独验收。
