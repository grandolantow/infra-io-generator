# 从偏好规则到可用绘图Skill：迭代计划

版本号仅为计划分段，不表示这些阶段已完成。

## 阶段0：v0.4规范冻结（本包）

产物：短主Skill、规则证据表、A/B/C/D配方、40条评价台账、语义与评测模板。

边界：原图尚未归档；旧“24条规则”包尚未获取和核验；不把历史助手的产物宣称计入已完成。

先补最小锚点资产40/31/33/34，必要时补23与28作参数和背景对照。核对论文/博客出处、图号和文件哈希，复用既有反馈，不要求用户重新打标。

## 阶段1：v0.5最小成图闭环

### 先做一题，不先做通用平台

选一个来源齐全、包含真实基线与改进关系的任务。它可以是已评价的40对应主题，但属于复现/校准，不叫未见论文泛化。

冻结同一份事实契约，实际输出三种结构：
- A：40式机制对照。
- B：主干或共享结构 + 差异模块展开。
- C：按该任务真实依赖选功能分块或直观机制。

均提供可查看HTML、可编辑SVG、来源和QA。三版不同布局不能删掉必须表达的事实。先由Agent完成技术与布局检查，再让用户只做一次选择；允许“都不可用”。

### 四配方冒烟回归

覆盖40式对照、31式主干、33式分块、34式状态路径。沿用熟悉主题验证工具链与规则是否可执行，不能以这些已见图证明迁移效果。

初步验收：真实图而非文字方案；关键事实无错；无明显裁切遮挡；确认后可局部修改，不让无关区域漂移。

## 阶段2：v0.6未见论文迁移与预算公平对照

### 固定任务集

采用5篇未进入规则示范的新论文，每篇2个任务，共10个任务：3篇开发集（6题）、2篇留出集（4题）。选择覆盖不同技术关系的论文，不必为追逐新年份而降低证据质量。

先固定任务说明、必需事实、来源、目标画布、预算和评分标准，再生成。

按论文与图族隔离开发和留出集；不能把同一原图的不同裁切或重绘当成未见任务。留出材料不进入案例检索库，不用于修规则。

### 先做公平Top-1对照

旧流程与v0.4规则使用相同执行模型、来源、画布、输出数及重试/工具预算，每题各一个最终成图，匿名随机顺序呈现。没有可调用的旧Skill时，以冻结的当前默认提示作为基线，并记录完整内容，不伪称旧包对照。

记录胜/平/负、均不可用、技术错误、结构性返工与局部返工。不能只挑最好看的个别案例报告。

### 再评多方案产品收益

在独立标记的试验中比较默认首选与三候选选择。记录：
- Top-1可用数：预先指定的首选有多少可直接用或只需局部修订。
- Best-of-3可用数：三张中至少一张可用的任务数。
- 首选命中数：系统首选是否等于用户最终选择。
- 生成候选总数、失败数、实际耗时和交互次数。

Best-of-3提升不能写成相同预算下的Skill单图能力提升。两种流程所有失败任务均保留在分母里。

### 小样本结论边界

10题是工程试验，不足以宣称统计显著或总体成功率已确定。开发集与留出集分别报告；留出结果只读一次用于验收。看过失败后据其修规则，这些题即转为回归集，下一轮另换留出题。

## 阶段3：v1.0业务任务与PPT集成

在模型架构验证后，增加NPU/推理任务：KV Cache状态与搬运、C+V串行与融合、设备任务依赖等。它们是迁移验证任务，不因模型图得到好评就视为已经可用。

将Skill作为 `huawei-html-ppt` 的图示子流程，而非另建完整PPT系统：

资料与页结论 → 图的事实契约 → 配方路由 → HTML/SVG → 验收 → 嵌入PPT → 必要时沿现有链路导出。

接入前读取仓库现状；本包未检查其真实API或目录。复用已有字体、页面数据模型与导出能力。先实现一个稳定入口，后补自动布局与复杂导出，避免过早建设图编辑器、图数据库或多Agent平台。

## 验收体系

### 硬门槛：不得被美观分抵消

- 关键事实、方向、汇合方式无错；不得虚构基线、参数或连接。
- 必要事实覆盖完整，来源能够定位。
- 交付能打开且可编辑；没有遮挡关键内容的版面错误。

### 软评价：尽量减少用户打标工作

以“选哪张 / 可用或需局部改或需重画 / 最大一个问题”为主。Agent可另行记录核心差异清晰度、路径可追踪性、信息层级、最终尺寸可读性四个诊断维度，但不能代替用户偏好判断。

### 暂定产品门槛（建议，不是实验结果）

在固定10题的阶段性版本中，关键技术错误为0，至少8题可直接使用或仅局部修订；另单列4题留出集结果。它只是继续投入的产品门槛，不是可靠性或统计结论。

## 如何把失败变成下一条规则

按事实、布局路由、层级、连线、密度、视觉、交付定位主要问题。每轮只改一到两个有证据的点，记录适用条件与反例；同时保留正例回归，避免修一张毁一类。

建议规则变更格式：

```text
观察：哪些独立任务出现了什么可复现问题？
条件：什么技术关系/画布/密度下发生？
动作：具体改变哪个规划或渲染行为？
边界：哪些任务不应应用此规则？
验证：修复案例、未见案例、历史正例各是什么结果？
```

用户明确约束可以直接执行；由样本推断的偏好必须保持“候选”，直到在独立任务上反复成立。不要因一张整体差评就创建整类技术禁令。

## 第五批素材的位置

第五批不是继续推进的前置条件，也不默认要求再做十张人工评价。只有出现明确覆盖缺口时才补新原图：每个新增样本说明要验证哪一条规则、为何现有锚点不足。保持原图与来源可追溯，按具体图去重。
