# 技术架构图绘制 Skill

规则版本：v0.4-draft。状态：首版执行规范，尚无生成质量验证结果。

## 目标

把来源中的技术关系变成读者能够追踪的架构图。默认采用浅色论文风，优先尝试40式机制对照；以31式主干展开、33式功能分块、34式直观机制作为补充。编号对应用户四批参考图评价，不代表已获取原图资产。

## 输入与边界

读取任务、受众、核心问题、来源材料、范围边界、目标画布及用户指定布局。
- 受众未指定时，按熟悉推理基础的AI Infra/NPU工程师组织。
- 页面或局部尺寸已给出时，以该尺寸为准，不强制16:9。
- 缺失的非关键视觉参数采用默认值；技术事实缺失不得猜补。
- 有明确参考版式时按该版式制作；只有实质取舍才增加备选。
- 修改已确认图时，只修改授权范围，保留其余布局和语义。

## 按需读取

1. 首次执行读 `references/rules-v0.4.md`。
2. 选布局时只读取 `references/layout-recipes.md` 的相关配方。
3. 技术契约使用 `templates/diagram-spec.json`；不要把模板空值当作已核实事实。
4. 记录验收使用 `templates/review-record.json`。
5. 迭代或评测时读 `references/iteration-plan.md`。
6. 引用偏好证据时读 `references/evidence-and-limits.md` 与 `data/ratings-40.json`。

## 执行流程

### 1. 明确讲解目标

写一条技术结论，确定图的输入、输出、展示边界和必要机制。区分“介绍整个模型”“解释一个机制”“比较两个方案”。不要先画框，再向框里填术语。

### 2. 建立来源支撑的语义契约

在 `diagram-spec.json` 中记录：
- 必须讲清的事实及来源定位。
- 必要模块、连接、汇合方式、残差或状态路径。
- 对照方案真实共有的部分和有证据的差异。
- 重要数值、维度与单位；未知项明确标记。
- 可以省略的内容与省略理由。

语义契约是所有候选共享的事实底稿。后续变更事实必须回到此处更新，并同步所有候选。

### 3. 路由布局

依次判断：
1. 存在真实的基线—改进、机制差异或方案关系：优先A，40式机制对照。
2. 主要任务是介绍完整模型、局部创新位置：B，31式主干+关键模块展开。
3. 多个并行或混合功能模块及汇合关系是重点：C，33式功能分块。
4. 记忆读写、状态演化、信息返回等概念路径是重点：D，34式直观机制。

A优先，但不得虚构基线或强制三列。可从A中只迁移对齐、共享视觉编码和变化强调方式。

### 4. 控制候选数量

- 默认交付一个推荐方案。
- 用户要求多方案，或确有难以提前消除的布局取舍时，通常生成三个方案。
- 三个方案必须在信息组织上实质不同，不得只换颜色、圆角或朝向。
- 每个方案都必须落实为实际成图，而非文字描述。
- 用户固定参考结构或只做局部修改时，不强制多方案。
- 各候选覆盖同一组必须表达的事实；不得通过删掉困难信息使某方案“更好看”。

### 5. 实现

默认生成自包含 `preview.html`，内联SVG、CSS与必要脚本；单独保存可编辑SVG和语义源文件。
- 不以生成式图片或截图作为默认生产源。
- 使用浅底、功能一致的视觉编码、明确的箭头和分组。
- 连接类型有区别；加和、拼接、选择、门控等汇合操作必须明确。
- 重复结构可用×N等表示，但不能改变跨层依赖。
- 参数就近标注；参数侧栏仅在任务确需时启用。
- 字体沿用宿主规范；用户PPT环境优先微软雅黑及可用回退字体，不随包分发字体。
- 输出尺寸、文字密度和间距以实际展示空间为准，不因元素多而无限缩小文字。

### 6. 验收与修复

先做技术检查，再做布局检查，最后做偏好匹配。
- 技术：事实有据，关键连接完整，方向与汇合方式正确，无伪造参数或基线。
- 结构：核心变化可定位，主路径可追踪，局部展开有对应关系。
- 视觉：实际画布下无重要文字遮挡、裁切或难读标签，色彩不成为唯一识别手段。
- 交付：HTML可打开，SVG可编辑，多方案切换有效，来源与原图/重绘身份分开记录。

有工具时做实际渲染检查并记录；未运行的检查必须写“未验证”。技术错误不得由视觉评分抵消。修复后重跑相关检查，不以反复润色代替纠错。

### 7. 交付与反馈

交付真实成图、可编辑源、来源和简短QA记录；多方案中注明推荐项及一个主要取舍。
反馈优先收集“选哪张 / 是否可用 / 最大一个问题”，不默认要求用户逐项长表打分。
用户确认一个版本后，仅对指定局部修改，避免其他区域漂移。

## 每个任务的交付目录

```text
output/<task-id>/
  brief.md
  sources.md
  diagram-spec.json
  preview.html
  variants/
    A.svg
    A.layout.json
    B.svg                  # 仅在生成多方案时存在
    B.layout.json
    C.svg
    C.layout.json
  qa.json
```

`diagram-spec.json` 保存事实；`*.layout.json` 保存各布局。HTML与后续PPTX尽量使用同一事实与布局来源，避免双份内容漂移。PPTX仅在用户需要且现有链路支持时导出。

## 停止与失败条件

来源不足时先交付有依据的部分并标明缺口，不编造边。关键正确性不通过时不得把候选标为“可用”。不声称仅通过格式检查就证明好看；不声称本规范已经安装、合入仓库或优于旧Skill。
